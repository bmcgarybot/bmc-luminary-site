# Payment integrity review — 2026-11-02

Two confirmed launch blockers are patched locally in `api/app.py`:

- Explicit Growth references cannot fall back to another territory. Only a delivered, unconverted, payer-matching sample with exactly five currently qualified saved rows can link automatically. Without a reference, there must be exactly one recent delivered sample; ambiguity, missing rows, or changed evidence leaves the actual receipt booked and the order in paid-needs-intake with a critical exception. Growth cannot fall through to unrelated lead auto-linking. Saved sample contents are unchanged.
- Refund events now serialize by payment intent, retain all signed event receipts, and account for successful refund object IDs once across event IDs. Pending/failed refunds do not reduce earned revenue. Distinct successful partial refunds accumulate; matching orders are marked partially refunded/refunded or refund review, and queued/in-progress tasks are blocked. A refund arriving before Checkout causes later receipt recording plus a fulfillment hold. Checkout retries cannot rebook a receipt after its order is refunded. Delayed-payment success stores paid order status even if the session payload still says unpaid.

Validation: 17 extracted production-handler fixture tests, 5 saved-sample evidence tests, and 4 fulfillment-claim tests pass; syntax compilation and workflow YAML parsing pass. Seven real PostgreSQL SQL-handler tests and a PostgreSQL 16 CI job were added, including concurrent receipt/refund delivery and scope holds. Signature verification is stubbed in these isolated SQL tests; the existing HTTP CI suite covers synthetic signed requests, including valid delivered-five checkout and fulfillment. Existing sampleless Growth HTTP assertions now require manual review and an unlinked, blocked intake, while preserving the separate paid-first Premium intake path. They were **not executed locally**: no database DSN/server is available. Local invocation reports seven explicit skips. Passing real PostgreSQL CI is required before release; this is not end-to-end launch evidence.

Boundaries: all refund transitions conservatively require manual review before any resumption, including failed/cancelled and partial refunds. No automatic refund or Stripe API call is introduced. A refund without a payment-intent reference receives a critical exception but cannot be correlated automatically; legacy ambiguous/multiple intent mappings are held across all matching orders. Historic refund accounting (especially previously booked pending/failed refunds) requires ledger reconciliation before release. Subscription invoice idempotency and disputes are outside this bounded patch. A payment already being delivered before the refund transaction acquires its order lock cannot be unsent.

No live Stripe/SMTP/network actions, hold releases, preview resends, new prices/products, SDK migration, GitHub writes, or root handoff edits were performed.
